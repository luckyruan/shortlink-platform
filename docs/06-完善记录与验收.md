# 短链接：完善记录与验收

日期：2026-10-04。

## 本轮修复

自动生成短码也可能命中之前的不存在缓存，因此新建成功后不仅自定义短码需要失效，自动短码也需要。

状态修改或创建属于事务时，在提交前删除 Redis 缓存，另一个请求可能查到旧数据库值并回填。因此使用 Spring TransactionSynchronization.afterCommit 在提交后失效；没有外层事务时直接失效，仓库保存自身事务已经结束。

新增回归检查：自动短码创建会失效缓存；事务同步回调触发前不失效，afterCommit 后才调用失效。原有测试和行为保留。

## 仍需明确

提交后失效减少一个竞态窗口，但不是强一致缓存方案。旧查询可能跨越失效后再回填；Redis 删除失败依然依赖 TTL。要求禁用立即严格生效时，应另做版本校验、读权威状态或更严格缓存策略。

访问计数是面向统计的聚合方案，不是精确账务系统；权限体系、真实 Redis 故障恢复和性能均需继续验证。

## 面试追加题

**为什么删缓存要在提交后？** 提交前删除后，其他读者仍能看见旧值再写入缓存；提交后删除让新的正常回源至少能看到已提交版本，但不解决所有并发读写。

**afterCommit 回调失败能回滚数据库吗？** 不能，数据库已经提交。需要可观测日志、重试/对账等机制；缓存删除不应被描述成与数据库的共同事务。
